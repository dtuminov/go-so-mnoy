## 🔴 Высокий приоритет

### 1. Слияние `Event` и `CompanySeeking` в единый `Activity`

**Согласовано к реализации.** Пока не сделано — не задерживать новые фичи
в этом домене, делать на следующей итерации.

**Зачем.** Сейчас сущности почти полностью симметричны, и каждая фича
(теги, фильтры, чаты, рассылка инвайтов, профильные кнопки, broadcast,
notify) реализуется парой зеркальных хэндлеров и сервисов. Каждая новая
фича умножается на 2; namespaces расходятся (`evch:` / `skch:`,
`tp:e:` / `tp:s:`, `ct:e:` / `ct:s:` …). Чем дольше тянем — тем дороже
рефакторинг.

**Эскиз модели.**

```text
Activity
  id, city_id, creator_id
  kind: enum('event','seeking')   -- дискриминатор
  title, body
  starts_at:  datetime?           -- когда происходит (NULL для seeking)
  expires_at: datetime            -- когда исчезает из ленты (всегда)
  place_text: string?
  chat_url:   string?
  status: enum
  published_notified, reminder_sent: bool
  created_at

ActivityMember           -- было: EventParticipant ⊕ CompanySeekingResponse
  id, activity_id, user_id
  status: enum            -- см. п. 2
  chat_invite_notified: bool
  created_at
  unique(activity_id, user_id)

activity_tags(activity_id, tag_id)
```

Семантика времени:
- **event**: `starts_at = выбранная дата`, `expires_at = starts_at + duration_min` (см. п. 4).
- **seeking**: `starts_at = NULL`, `expires_at = created_at + N дней`.

**Что упрощается после миграции:**
- Один builder ленты, один FSM создания (kind на первом шаге → развилка
  по полям), один tag picker, один `event_chat`, один
  `chat_invite_notify`, один `notify_actor_about_new_member` без
  параметра `entity_kind`.
- Один callback namespace вместо параллельных пар.

**Что не забыть в миграции (`007_unify_activities`):**
- Перенос данных из `events` и `company_seekings` (с проставлением `kind`).
- Перенос `event_participants` / `company_seeking_responses` →
  `activity_members`.
- Перенос `event_tags` / `seeking_tags` → `activity_tags` (объединение).
- Сохранить старые таблицы как `*_legacy` на одну ревизию — для отката.
- Откатная миграция через `_legacy` (downgrade без потерь).

**Связанные файлы:** все ORM в `bot/models/`, миграции 002/005/006,
почти все хэндлеры и сервисы (см. `STRUCTURE.md`).

### 2. Открытые vs закрытые (private) события — подтверждение участия

**Зачем.** Сейчас `EventParticipant.status` всегда `'joined'` —
поле мёртвое. Хотим использовать его для двух типов событий:

- **Open** — пользователь нажал «Иду» → сразу `joined`, текущее
  поведение.
- **Private** — пользователь нажал «Хочу» → создаётся запись со статусом
  `pending`, организатору приходит DM «X хочет присоединиться к
  «Название»» с inline-кнопками `✅ Подтвердить` / `❌ Отклонить`.
  По подтверждению — `joined`, по отказу — `rejected` (или просто
  удаление; см. ниже).

**Как ложится на схему.**
- Новое поле на `Event` (или `Activity` после п. 1):
  `visibility: enum('open','private')` (по умолчанию `open`).
- `EventParticipant.status` (или `ActivityMember.status`):
  `enum('pending','joined','rejected')`. Сейчас все живые записи —
  `joined`.
- Для счётчика участников/ленты — учитывать только `joined`.
- Для рассылки чата (`chat_invite_notify`) — тоже только `joined`.

**Открытые вопросы (нужно решить до реализации).**

1. **Дефолт visibility** — open или private? Гипотеза продукта: open
   (низкий барьер для роста), private — опция для микро-комьюнити и
   для модерируемых событий типа нетворкинга. Скорее всего: дефолт
   `open`, выбор на отдельном шаге FSM.
2. **Можно ли менять visibility после создания?** Если да — что с
   текущими `pending`-заявками при переходе `private → open`? Авто-апрув?
3. **Лимит участников** для private — задаётся орг-ом или нет? Если
   да — это новое поле `max_participants`.
4. **UX для пользователя на стороне `pending`.** Кнопка «Иду» становится
   «Заявка отправлена» (disabled) или «Отозвать заявку» (отмена).
   Лента не показывает «Иду» дважды.
5. **Уведомление пользователю при результате.** При `joined` — DM с
   приглашением в чат (если `chat_url` есть). При `rejected` — DM
   «Организатор не подтвердил» (опционально с возможностью попробовать
   снова или нет?). Спам-чувствительно.
6. **Reject = удаление или отдельный статус?** Если статус — не
   позволяем повторно подать заявку (или позволяем, но с задержкой?).
   Если удаление — повторить можно сразу. Влияет на UX.
7. **`chat_url` доступ.** Для private-событий ссылка должна быть видна
   **только после `joined`** — а не сразу при `pending`. Текущая логика
   `viewer_joined` пропускает любого с записью; нужно фильтровать по
   `status='joined'`.
8. **Что показывает организатор в профиле?** Сейчас «👥 Участники» — для
   private надо разделить «Заявки на подтверждение (N)» и «Подтверждено
   (M)». Или один список с группировкой.
9. **Cancel события с `pending`-заявками.** Скорее всего просто
   уведомление и зачистка, как с обычными участниками.
10. **CompanySeeking** — нужна ли private/open там? Заявки «ищу
    компанию» по природе скорее всегда open, но при унификации —
    единый механизм может пригодиться (например, автор хочет
    «фильтровать кандидатов»).

**Рекомендация по последовательности:**
1. Сначала **слияние (п. 1)** — иначе придётся реализовывать
   visibility/approval дважды.
2. На едином `Activity` — добавить `visibility` и расширить
   `ActivityMember.status`.
3. UX и нотификации — отдельным коммитом поверх схемы.

## 🟡 Средний приоритет

### 3. `status` как Postgres ENUM (или CHECK)

**Зачем.** Сейчас `Event.status`, `CompanySeeking.status`,
`EventParticipant.status` — все `String(32)`. БД не знает про допустимые
значения, всё держится на константах в `bot/constants.py`. Опечатка в
коде = тихий баг, миграции не обнаружат.

**Как.**
- Postgres `CREATE TYPE event_status AS ENUM (...)` + `ALTER COLUMN ... TYPE event_status USING ...::event_status`.
- Альтернатива дешевле в миграции: `CHECK (status IN (...))`.

**Когда делать.** Если будем сливать в `Activity` (п. 1) — сразу
закладывать `activity_status` ENUM в новой схеме, отдельную миграцию для
текущих таблиц можно не делать.

**Связанные файлы:** `bot/constants.py`, миграции 002/006.

### 4. У события нет конца (`ends_at` / `duration_min`)

**Зачем.** Лента фильтрует `Event.starts_at >= now()`, поэтому событие
**пропадает в момент начала**. Реальные потери:
- Юзер увидел в 18:55 событие на 19:00, не успел нажать → в 19:00 кнопка
  исчезла.
- Длинные ивенты (бар-хоппинг 19:00–02:00) пропадают через час, хотя люди
  могли бы присоединиться по дороге.

**Решения, по убыванию инвазивности.**
- (a) **Мин. изменение** — `expires_at` на событии = `starts_at + 2h`
  по умолчанию (без UI-вопроса). Фильтр ленты — по `expires_at`.
- (b) Спрашивать `duration_min` числом отдельным шагом FSM (1 шаг,
  кнопки 1ч/2ч/3ч/«указать»).
- (c) Полноценный `ends_at` ввод — лишний шаг, не стоит свечек на старте.

**Когда делать.** Логично совместить с п. 1 — в `Activity.expires_at`
у события это будет естественное поле, а у seeking оно уже есть.
Минимальная версия (a) — буквально 1 миграция и 1 строка в фильтре, можно
и до унификации.

**Связанные файлы:** `bot/services/events.py`, `bot/handlers/create_event.py`.

### 5. Композитный индекс на `company_seekings`

**Зачем.** У `events` миграция 002 создала
`(city_id, status, starts_at)` — покрывает запрос ленты. У
`company_seekings` симметричный запрос:

```sql
WHERE city_id = ? AND status = 'published' AND expires_at >= now()
ORDER BY created_at DESC
```

…но индексов только по одиночным колонкам. Стоит:

```sql
CREATE INDEX ix_company_seekings_city_status_expires
  ON company_seekings (city_id, status, expires_at);
```

**Когда делать.** Можно отдельной маленькой миграцией прямо сейчас или
дождаться унификации (тогда индекс ставится сразу на `Activity`).

## 🟢 Низкий приоритет / на подумать

### 6. Аудит модерации (`ModerationLog`)

**Зачем.** При `approve` / `reject` события статус меняется молча — кто и
когда одобрил, не сохраняется. Если завтра канал получит спам, ты не
узнаешь, чья ошибка модерации. Нужно, как только модерация перестанет
быть «один человек на коленке».

**Эскиз:**

```text
ModerationLog
  id, activity_id, moderator_id (User.id)
  action: enum('approve','reject','cancel')
  comment: text?
  created_at
```

**Не блокирующее**, но если канал реально пойдёт в рост — пригодится в
первые недели.

### 7. `chat_invite_notified` — закладывает поведение «один shot на чат»

**Зачем.** Сейчас флаг `chat_invite_notified` ставится `true` при первом
заполнении `chat_url`. Если орг удалил ссылку (`value → NULL`) и потом
добавил **другую** — рассылка пойдёт только новым участникам, а старые
останутся со старой (или без) ссылкой. Согласовано как ожидаемое
поведение, но это ловушка для будущих изменений.

**Идея на будущее (НЕ делать сейчас).** Заменить boolean на
`last_invite_chat_url_hash: string?` — короткий хэш `chat_url` на
момент рассылки. Тогда смена ссылки → `hash` отличается → можно решить,
рассылать ли заново. Без этого — текущее поведение фиксированное.
